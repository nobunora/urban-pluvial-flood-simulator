# v0.1 Phase 4 implementation report

## Disposition

`implementation-complete / hydraulic acceptance validation pending`

The Phase 4 Adaptive execution path is implemented through classification,
HydroMT-SFINCS quadtree/subgrid model build, native SFINCS face-result reading,
normalization, result rendering/inspection, and coordinator orchestration.

Adaptive is user-selectable through an explicit UI ON/OFF control. The UI default
is OFF and therefore preserves the established Full 1 m execution path. The
public API route accepts Adaptive only when the request explicitly selects it;
the conservative `RunCoordinator` constructor default remains disabled for
internal/test callers. Hydraulic acceptance evidence is still pending.

## Validated Adaptive foundations

The production deterministic Adaptive classifier starts from the canonical
Full 1 m source raster and only coarsens complete safe blocks successively:

```text
1 m -> 2 m -> 4 m -> 8 m
```

The implementation remains structurally extensible to 16/32 m, but those levels
are not part of the current production policy.

Current invariants include:

- every source cell begins at 1 m before any merge is considered;
- building and road source cells remain at 1 m;
- the projected within-2 m hard-feature rule remains at <=2 m;
- the authoritative Full 1 m `sfincs_mask` is reused as the hard-boundary-zone
  source, preserving both building boundaries (0/1) and the immutable analysis
  edge (1/3);
- optional pre-existing resolution ceilings and native-structure masks survive
  the prepared-grid cache and are passed into the Adaptive classifier;
- target protection is configurable; the production default keeps 0-100 m at
  1 m and 100-250 m at <=2 m;
- terrain structure is protected using local curvature/extrema plus metric
  refinement buffers, while uniform planar slopes remain eligible for
  coarsening;
- terrain plane-fit RMSE, maximum residual, curvature and detrended relief
  thresholds are versioned by a deterministic threshold identity;
- coarsening occurs in the required direction 1->2->4->8 rather than by
  starting coarse and refining;
- quadtree refinement is 2:1 balanced;
- each source cell is covered exactly once by the final source-overlapping
  quadtree face layout;
- no source-overlapping hydraulic face may be coarser than the classifier target
  it covers;
- outside-domain padding has zero source overlap and no hydraulic contribution;
- authority-less local AEQD CRS is preserved through the quadtree NetCDF writer
  without inventing EPSG metadata.

The pinned HydroMT-SFINCS 2.0.0rc3 hierarchy defects discovered during actual
quadtree construction remain handled by the staged/rebased quadtree seam in
`adaptive_quadtree.py`; upstream rc3 code is not monkey-patched.

## Canonical Adaptive model build

The production implementation is
`floodsim.sfincs.model_builder.AdaptiveSfincsModelBuilder`.

The older `floodsim.sfincs.adaptive_model_builder.SfincsAdaptiveModelBuilder`
name is now only a backward-compatible re-export of the canonical builder, so
there is no second model-build implementation.

The builder:

1. creates the classifier-driven pinned-rc3 quadtree;
2. retains canonical Full 1 m elevation as the subgrid terrain source;
3. retains canonical Full 1 m Manning values as the subgrid roughness source;
4. creates the HydroMT-SFINCS subgrid table;
5. keeps the mass-conserving Full 1 m roof-allocation precipitation raster as
   distributed meteorological forcing;
6. enables `storevel=1`;
7. enables `storehsubgrid=1`, required by SFINCS to emit `h` / `hmax`
   during subgrid runs;
8. enables `storezvolume=1`, producing SFINCS
   `subgrid_volume(time, nmesh2d_face)` for hydraulic-volume diagnostics;
9. writes quadtree, subgrid, precipitation, configuration and a deterministic
   `adaptive_face_layout.npz` artifact.

The model build report records grid type, 1/2/4/8 m cell counts (including
explicit zero counts), total/equivalent cells, reduction ratio, protection
diagnostics, threshold identity, subgrid configuration, forcing/mass
diagnostics, velocity/depth/volume output switches and unsupported-physics
facts.

## Native face-result contract

Adaptive results are not expanded into Full 1 m time-by-time arrays.

`read_quadtree_result()` reads native SFINCS face data:

```text
h(time, nmesh2d_face)
hmax(timemax, nmesh2d_face)
zb(nmesh2d_face)
msk(nmesh2d_face)
u/v(time, nmesh2d_face), when present
subgrid_volume(time, nmesh2d_face), when present
```

It validates face count/order against `adaptive_face_layout.npz`, excludes
boundary-control/inactive faces from ordinary result values, applies the same
finite/negative-depth policy as the Full reader, reconstructs missing active
`hmax` from time-depth only when necessary, and validates non-negative finite
subgrid volume.

`normalize_quadtree_result()` persists
`normalized_adaptive_faces.npz` in native face order. The subgrid-volume
series is retained in that native artifact for validation use; it is not added
to the public result-metadata schema.

## Result UI/API compatibility

The result loader auto-detects regular-dense versus `quadtree_faces` storage.

For Adaptive runs:

- maximum-depth PNG expands only the selected face field at render time;
- time-depth PNG expands only the requested time slice;
- grid-resolution PNG is derived from native face resolution;
- point inspection resolves the requested source-grid point to exactly one
  native face and returns the native face value;
- flow-vector GeoJSON uses native quadtree face centers and face velocity.

The complete Adaptive time series therefore remains face-native instead of
defeating the cell-count reduction by materializing Full 1 m arrays.

## Coordinator integration and safety gate

`RunCoordinator` now has a complete Adaptive branch:

```text
common Full 1 m normalized source/prepared cache
→ Adaptive classifier
→ quadtree/subgrid builder
→ native SFINCS execution
→ quadtree face reader
→ face-native normalizer
→ existing result API/view layer
```

The normalized Full 1 m terrain/building/road/roof-rain source remains shared
between Full and Adaptive, so provider acquisition and prepared-grid caching are
not duplicated.

Default constructor capability remains conservative:

```python
RunCoordinator(adaptive_enabled=False)
```

The public API route explicitly enables Adaptive capability, while the UI
defaults to `Adaptive OFF` and sends `full_1m`. Selecting `Adaptive ON`
sends `adaptive`, which is the only case where the static Adaptive classifier
and its terrain/structure/target/hard-boundary rules execute.

Tests verify both the disabled/off behavior and the enabled Adaptive
orchestration path, including cache preservation and forwarding of hard
boundaries, existing resolution ceilings and native-structure constraints.

## Specification section 20.6 validation gate

The repository now implements the exact numerical acceptance thresholds from the
specification:

- flooded-area IoU at depth >= 0.05 m: **>= 0.90**;
- median absolute maximum-depth difference on mutually wet cells:
  **<= 0.03 m**;
- p95 absolute maximum-depth difference: **<= 0.10 m**;
- accounted final surface-water-volume relative difference: **<= 2%**;
- important road/channel connectivity class preserved;
- Adaptive cell count lower than Full for at least an open-area benchmark class.

`floodsim.validation.adaptive_accuracy` performs the numerical comparison.
Only the maximum-depth face field is projected to the source 1 m comparison
plane; the stored Adaptive time series remains face-native.

The validator deliberately does **not** infer the volume criterion from final
storage alone. SFINCS exposes `subgrid_volume` for subgrid storage, but the
current reviewed map-output path does not provide a confirmed cumulative
open-boundary-outflow quantity that can be substituted safely. Therefore:

- raw final Full/Adaptive storage is available as a diagnostic;
- the <=2% criterion is evaluated only when both comparison volumes have already
  been accounted for open-boundary outflow;
- missing accounted-volume evidence leaves that criterion unresolved, not PASS;
- missing documented connectivity evidence likewise remains unresolved, not PASS.

The suite itself can only PASS when every required criterion is positively
established and an open-area benchmark demonstrates actual cell reduction.

## Deterministic real-SFINCS benchmark runner

The repository defines three fixed 64 m × 64 m representative fixtures:

- `open_area`: smooth open terrain for proving actual cell reduction;
- `urban_obstacle`: blocked building footprint plus mass-conserving roof runoff;
- `road_channel`: a mapped 1 m road corridor with a deterministic depressed flow path.

Each fixture uses the same normalized Full 1 m source contract and a fixed
30-minute, 120 mm/h rainfall forcing for both model modes.

A permitted local SFINCS executable can run a paired Full + Adaptive case with:

```bash
python -m scripts.run_adaptive_benchmark \
  --case open_area \
  --out-dir <output>/open_area \
  --sfincs-exe <existing-sfincs.exe>
```

Repeat with `urban_obstacle` and `road_channel`. The runner builds both models,
executes the same engine serially, reads both native result formats, evaluates
all currently provable section 20.6 metrics and writes
`benchmark_report.json`.

It does not manufacture open-boundary-outflow accounting or connectivity
evidence. Those optional values can be supplied only after they are established:

```bash
python -m scripts.run_adaptive_benchmark \
  --case road_channel \
  --out-dir <output>/road_channel \
  --sfincs-exe <existing-sfincs.exe> \
  --full-accounted-volume-m3 <value> \
  --adaptive-accounted-volume-m3 <value> \
  --connectivity-preserved true
```

## Local real-result gate command

If Full and Adaptive result files already exist independently, one benchmark can
instead be evaluated with:

```bash
python -m scripts.adaptive_accuracy_gate \
  --full-map <full>/sfincs_map.nc \
  --adaptive-map <adaptive>/sfincs_map.nc \
  --adaptive-layout <adaptive>/adaptive_face_layout.npz \
  --benchmark-name <name> \
  --benchmark-class open_area \
  --full-accounted-volume-m3 <value> \
  --adaptive-accounted-volume-m3 <value> \
  --connectivity-preserved true \
  --output adaptive-validation.json
```

The command writes the complete JSON report and exits non-zero unless every
criterion for that case is proven. Omitting volume/connectivity evidence is
allowed for diagnostics but cannot produce a passing gate.

The existing `scripts/adaptive_sfincs_smoke.py` now uses the canonical builder
and can use an already-permitted local SFINCS executable without downloading or
redistributing an engine.

## Remaining Phase 4 evidence

The implementation work is no longer blocked on model serialization or result
format support. Because the production classifier policy was updated to the
terrain-first 1/2/4/8 m policy above, the remaining Phase 4 acceptance evidence
requires fresh real-SFINCS runs using this exact policy:

1. rerun representative Full 1 m and Adaptive benchmark pairs with the new
   production classifier;
2. record the exact engine/build and benchmark inputs;
3. establish a defensible open-boundary-outflow-accounted volume comparison;
4. document important road/channel connectivity preservation for applicable
   benchmark cases;
5. confirm at least one open-area benchmark reduces hydraulic cell count;
6. run the section 20.6 gate over the benchmark corpus;
7. only if the suite passes, change the default public Adaptive feature gate.

Until those steps are complete, Adaptive remains implemented but experimental
and hidden by default, exactly as required by the specification.
