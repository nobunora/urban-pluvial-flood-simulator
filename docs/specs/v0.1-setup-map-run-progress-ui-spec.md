# Urban Pluvial Flood Simulator v0.1 — Setup Map and Progress UX Specification

> Status: Active UX contract for PR #12
>
> Scope: Full 1 m local review flow only.
>
> This document defines **what the user sees and can do** for the setup-map and run-progress improvement. Implementation ownership and file boundaries are defined separately in `docs/specs/v0.1-setup-map-run-progress-spec.md`.

---

## 1. User problem

The current review UI has two usability problems:

1. selecting a place by latitude/longitude alone is difficult for ordinary users;
2. long preprocessing/SFINCS execution can look stalled because the user sees only a coarse stage label.

The improved UI must solve both without changing the hydraulic model, providers, RunConfig contract, result semantics, or Adaptive availability.

---

## 2. Required outcome

A user must be able to:

1. open SETUP and immediately see a map;
2. click the map to select the analysis center;
3. see the selected center represented by a marker;
4. see the selected analysis range represented by a square frame;
5. change ±250/500/1000/2000 m and see the frame resize immediately;
6. still edit latitude/longitude directly when desired;
7. start the Full 1 m analysis;
8. understand which processing step is currently running;
9. see which major input/intermediate data items have already been acquired or generated;
10. distinguish “application is still alive and SFINCS is still running” from “the process has stopped”;
11. see elapsed time during SFINCS calculation;
12. reach the existing RESULT view without regression.

---

## 3. SETUP map

### 3.1 Visibility

The map is visible in SETUP next to the condition controls.

The map should occupy enough screen area that a user can recognize streets/landmarks and choose a center spatially.

Base map:

- GSI standard map tiles;
- MapLibre GL JS;
- visible GSI attribution.

### 3.2 Center selection

Visible helper text:

> 地図をクリックして解析中心を選択できます。四角い枠が解析範囲です。

Clicking the map while no run is active:

- changes the analysis center;
- moves the marker;
- updates latitude and longitude fields;
- moves the analysis-range frame.

Latitude/longitude fields remain available.

### 3.3 Analysis range

Existing preset choices remain:

- ±250 m
- ±500 m
- ±1000 m
- ±2000 m

The map displays the selected range as a square:

- translucent fill;
- clear outline;
- centered on the selected point.

Changing the range updates the square immediately.

The square is the same area that will be submitted to the backend; the UI must not maintain a different hidden geometry.

### 3.4 During a run

Once a run is active:

- location/range/rain/duration controls are not editable;
- map clicks do not alter the active analysis center;
- the currently selected map/range may remain visible for context.

---

## 4. Run progress

### 4.1 Purpose

The run-progress display explains:

- what the application is doing now;
- what major work has already completed;
- what data/artifact each major phase produced;
- whether the local application is still responding.

It must not claim numerical solver progress that the engine does not actually provide.

### 4.2 Ordered stages

The user-facing progress sequence is:

1. 受付
2. 入力確認
3. 標高取得
4. 建物・道路取得
5. 降雨準備
6. 地形前処理
7. 屋根雨水配分
8. 1 m格子構築
9. SFINCSモデル構築
10. エンジン確認
11. SFINCS計算
12. 結果読込
13. 完了

The current stage is visually highlighted.

Completed stages and pending stages must be visually distinguishable.

### 4.3 Data/artifact badges

The UI displays compact visual badges for major acquired/generated items:

- 標高
- 建物・道路
- 雨
- 1 m格子
- モデル
- SFINCS
- 計算
- 結果
- 地図

Each badge includes both an icon/symbol and text.

A badge changes appearance when its stage has completed.

These badges mean “workflow step completed”; they are not a scientific-quality certification.

### 4.4 Application-stage progress

The UI may display the known application pipeline position, for example:

> 工程 8 / 13

This value means application-stage position only.

It must not be labelled as hydraulic solver completion percentage.

---

## 5. SFINCS execution state

SFINCS execution can take long enough to appear stopped.

While the current stage is SFINCS calculation, the UI must show:

- text `SFINCS計算中`;
- elapsed time since the browser observed this stage;
- freshness of the latest successful backend status response;
- an indeterminate activity bar until official SFINCS stdout progress is observed;
- once official `% complete` output is observed, a determinate progress bar and that actual percentage;
- a remaining-time estimate computed from actual elapsed time divided by actual progress fraction.

Example after progress is available:

> SFINCS計算中 — 40% — 経過 00:12

> 状態確認: 1秒以内 / 残り目安 約00:18（実進捗から推定）

The UI must **not** fabricate progress or use the engine's rough remaining-seconds field as the sole ETA.

---

## 6. Failure/cancellation

If the run fails:

- the failed state is visible;
- the existing failure code/message remains available;
- the UI does not show completion.

If cancellation is requested:

- cancellation state is visible until terminal cancellation.

The progress display must not hide errors behind animation.

---

## 7. RESULT transition

After successful completion:

- the existing RESULT flow remains unchanged;
- maximum-depth map, time-depth layer, grid layer, point inspection, provenance and limitations continue to work;
- “新しい解析” returns to SETUP while retaining prior inputs as already specified.

---

## 8. Accessibility and truthfulness

The UI must:

- include text labels in addition to icons;
- provide an accessible label for the setup map;
- not rely only on color to distinguish meaning;
- respect reduced-motion preference while the progress state is indeterminate;
- distinguish “backend responded recently” from “solver has made known numerical progress.”

---

## 9. Non-goals for this slice

This change does not include:

- address/geocoder search;
- freehand/free-rectangle drawing;
- Adaptive implementation;
- new backend endpoints;
- new dependencies;
- guessed/undocumented solver progress; official SFINCS `% complete` stdout parsing is allowed by the active runtime-progress contract;
- provider changes;
- hydraulic/grid/rainfall changes;
- broad UI redesign;
- final application-wide state-management refactor.

---

## 10. Acceptance criteria

The slice is user-acceptable when:

1. setup map appears in the actual Windows browser;
2. clicking a map point updates latitude/longitude and marker;
3. the analysis square is visible;
4. switching all four preset ranges visibly changes the square;
5. active run prevents setup mutation;
6. run-stage visualization advances as backend stage changes;
7. acquired/generated-data badges become visually complete as stages pass;
8. SFINCS stage shows elapsed time and indeterminate activity until real progress is available;
9. when official SFINCS progress is available, the real percentage and elapsed/progress-based ETA are displayed; no fake percentage is displayed;
10. a real Full 1 m run still reaches RESULT;
11. accepted RESULT behavior has no regression.
