# v0.1 Result viewport cache specification

> Status: Proposed product contract
>
> Canonical language: English
>
> Detailed implementation companion: `v0.1-result-viewport-cache-implementation-spec.md`

## Goal

Keep one-minute SFINCS output responsive while a user inspects a location, moves
the time slider, and then pans toward an area of interest. Large Full 1 m runs
MUST NOT require all times and all cells to be loaded into memory before RESULT
is usable.

## Scope

- Full 1 m, 2 m, and 4 m uniform runs only; Adaptive is not part of this
  contract.
- Existing `sfincs_map.nc` is the authoritative hydraulic result artifact.
- RESULT map layers, time slider, vectors, and point inspection.
- Recovery of a solver-complete run whose old full-array normalization failed.

## Non-goals

- Reducing the temporal output interval. One-minute SFINCS output remains
  available without interpolation or thinning.
- Re-running SFINCS merely to make results viewable.
- Changing hydraulic equations, rainfall input, provider policy, or UI layout.

## Confirmed incident and design decision

### Incident: solver-complete results became unavailable

The observed Full 1 m run `5211de6c-d9c9-4b2a-9f37-d5b2a7212226` completed
SFINCS successfully, but failed in `READING_RESULTS`. Its retained
`sfincs_map.nc` contains 21 one-minute frames of `8000 x 8000` cells, with
`(1, 2000, 2000)` NetCDF chunks. The former completion path decoded all
time-depth values and attempted to construct a dense result artifact. The
velocity allocation alone requested approximately 5.01 GiB, followed by
prolonged paging while attempting recovery. This is a result-viewing failure,
not a hydraulic-calculation failure.

The system MUST therefore treat successful SFINCS output as complete before
any optional display cache is built. An intact NetCDF from a legacy
`READING_RESULTS` failure MUST be recoverable without re-running SFINCS.

### Selected solution: source-preserving out-of-core viewport rendering

The selected design is a server-side, source-preserving, out-of-core viewer:

1. Retain `sfincs_map.nc` as the only authoritative regular-grid result.
2. Persist compact metadata and a source descriptor at run completion; do not
   create a dense all-time NPZ for new regular runs.
3. Read, decode, colour, and composite only source chunks intersecting the
   requested viewport and selected native minute.
4. Cache decoded chunks and rendered payloads by bytes under a dynamic memory
   budget; when no cache fits, stream one chunk at a time.
5. Run selected-time/visible-area work before speculative work. Cancel queued
   work from obsolete pan or time selections.

This is preferred over (a) loading all frames, which caused the incident;
(b) reducing one-minute output, which loses required evidence; and (c)
creating an additional Zarr/PNG pyramid at completion, which duplicates a
multi-gigabyte result and delays availability. A later offline export cache is
permitted, but MUST remain optional and never gate completion.

### Research basis

This decision follows established large-raster visualization practice. GPlates
reports that arbitrarily large rasters may not fit memory and uses a
multiresolution tile partition so only visible tiles at the necessary
resolution are resident. Its source format coverage includes NetCDF. The
current product keeps the same visible-tile residency principle, but preserves
native numeric one-minute values rather than substituting a coarser source.

Scientific NetCDF distribution literature also treats chunked, compressed
NetCDF as the data product rather than an invitation to decode the whole data
set. The selected design aligns reads to those chunks and avoids a second full
result copy. More generally, large spatiotemporal visualization research
reports that exploratory interactions become costly across high resolution and
many timestamps; prioritising the current selection before background work is
therefore a product requirement, not merely an optimisation.

References:

- Müller et al., *GPlates: Building a Virtual Earth Through Deep Time* (2018),
  section 8: [article](https://agupubs.onlinelibrary.wiley.com/doi/10.1029/2018GC007584).
- King et al., *A Comprehensive Northern Hemisphere Particle Microphysics Data
  Set From the Precipitation Imaging Package* (2024), NetCDF chunking and
  compression: [article](https://agupubs.onlinelibrary.wiley.com/doi/10.1029/2024EA003538).
- Liu et al., *Large-Scale Spatiotemporal Kernel Density Visualization* (2025),
  interactive high-resolution, many-timestamp scalability:
  [article](https://ieeexplore.ieee.org/document/11113195/).

## Why this cannot be applied unchanged

The research pattern is not a drop-in replacement for the current application.
The existing regular-result contract is a dense in-memory object with arrays
equivalent to:

```text
depth[time, row, column]
max_depth[row, column]
terrain[row, column]
mask[row, column]
velocity_u[time, row, column]
velocity_v[time, row, column]
```

The regular result reader currently constructs those arrays before the
normalizer writes `normalized_full_1m.npz`. The rendering, vector, and point
inspection paths then expect ordinary NumPy indexing over that NPZ. This makes
small runs simple, but it couples four distinct responsibilities: solver
completion, source validation, persistence, and display decoding.

Consequently, replacing the reader with a NetCDF descriptor alone would break
the current renderer: it expects `depth[time]` to already be a complete raster,
the vector path expects complete depth and velocity arrays, and archive export
expects a `normalized_arrays` NPZ. Conversely, retaining those contracts and
adding a cache underneath them still forces a complete frame or time axis to be
materialised at the boundary, recreating the memory failure. A generic
multiresolution pyramid is also not sufficient: it can accelerate map images,
but cannot by itself provide exact one-minute numerical point inspection or
native flow vectors.

## Required adaptation of the application contract

The application MUST split the present dense-result contract into a source
contract and view operations. This is a behavioural replacement for new
regular-grid runs; it is not a change to the hydraulic model or to the user
interface.

| Current coupling | Required replacement | Result |
| --- | --- | --- |
| SFINCS completion waits for full `h/u/v` decoding and NPZ creation | Completion performs dimension/variable validation and writes a compact source descriptor | Solver-complete data is immediately a completed result |
| `normalized_full_1m.npz` is the only regular display source | The descriptor identifies immutable `sfincs_map.nc`, grid geometry, time axis, chunks, and schema revision | New runs have no all-time duplicate result file |
| Renderer receives a whole `depth[time]` raster | Renderer requests `render_layer(viewport, time, layer)` | Only intersecting source chunks are decoded and composited |
| Vector endpoint receives whole depth/u/v arrays | Vector endpoint requests `read_vectors(viewport, time, spacing)` | Sampling occurs after bounded source reads; 1/2/4 m display density stays consistent |
| Point inspector reads `depth[:, row, column]` from NPZ | Inspector reads one cell across the native time axis in bounded slices | All one-minute values remain exact without loading the map |
| Result export assumes a normalized NPZ | Export includes the source descriptor and NetCDF, or preserves a legacy NPZ archive | Existing archives remain usable; new exports remain self-contained |

### Completion and recovery boundary

After SFINCS returns success, the completion worker MUST only perform bounded
validation. It verifies variable names, dimensions, time coordinates, mask,
and chunk metadata; any scan for quality metadata is performed one source chunk
at a time. It then writes `result_metadata.json` and a descriptor. The run
becomes `COMPLETE` at that point.

Display decoding, cache failure, or prefetch failure occurs after completion
and MUST be reported as a recoverable result-view error. It MUST NOT change the
calculation state to failed. For a legacy run stuck at `READING_RESULTS`, the
same bounded finalization is run against its retained NetCDF, then the manifest
is repaired to `COMPLETE`; SFINCS is not launched.

### Source descriptor requirements

The descriptor is intentionally small and versioned. It MUST contain the
NetCDF filename and immutable file identity, grid width/height, uniform block
size, geographic bounds, time values, variable names, source chunk shape,
available layers, and result-cache schema revision. It MUST NOT contain a
time-by-grid numerical array. A change to the source file identity or schema
revision invalidates cached chunks safely.

### Additional confirmed integration constraint

The current map image URLs contain a layer and, for depth, a time index, but
no viewport bounds. Map movement is currently communicated only to the vector
request. Therefore server-side chunk reads alone will not reduce depth-image
work until the image route and browser client gain a viewport/tile contract.
In addition, the archive format admits exactly one NPZ member. The new
descriptor/NetCDF format requires a versioned archive schema, not a renamed
NPZ member. These two contracts MUST be migrated together with the result
reader; partial deployment is prohibited.

### Bounded display operations

For a map layer, the server intersects the requested geographic viewport with
the grid, maps it to source chunk coordinates, and reads one time and one chunk
at a time. Each chunk is normalised under the existing dry/no-data policy,
coloured, and copied into the requested image. The decoded chunk is admitted
to cache only if the dynamic budget permits it. A no-cache render remains
correct, though slower.

For vectors, the same intersection is used for `h`, `u`, and `v`; source reads
remain aligned with the time/chunk layout. Sampling follows reading, rather
than reducing stored hydraulic values. For point inspection, the server reads a
single `(row, column)` location over time in bounded blocks and returns every
native one-minute value. These operations preserve numerical values; only the
map image and arrow density are display products.

## Chunk layout, indexing, and preprocessing evaluation

### Measured baseline

On the retained incident output, a cold local read of one compressed
`2000 x 2000` float32 `h` chunk (16 MB decoded) took 0.127 s; a second spatial
chunk took 0.115 s. Reading the matching `u` and `v` chunks together (32 MB
decoded) took 0.268 s. These are local-machine measurements, not a latency
guarantee. They show that source-chunk reads are practical for a narrow
viewport, but an unbounded whole-map request would still read 16 chunks per
variable and is unsuitable as an interaction strategy.

### Options considered

| Option | Added storage / completion cost | Interaction effect | Decision |
| --- | --- | --- | --- |
| Read existing NetCDF chunks with metadata index and RAM cache | Descriptor only; no duplicate hydraulic data | First view reads only intersecting chunks; repeat/pan-neighbour views are fast from cache | **Adopt** |
| Build a spatial tree over every cell | Extra build and index storage; duplicates regular-grid coordinates | No pruning benefit: a regular grid converts viewport bounds to row/column arithmetic | Reject |
| Build a tree over source chunks | Small descriptor-sized index | Equivalent to arithmetic chunk-row/chunk-column lookup; useful only as diagnostics | Do not build a separate tree |
| Rechunk/rewrite NetCDF at completion | Writes another multi-GB data set and delays result availability | May improve a different future access pattern, but does not remove decompression or cache needs | Defer; optional offline tool only |
| Generate depth PNG tile pyramid for all times | Potentially very large derived output plus long completion work | Fast imagery, but loses native values for inspection/vectors and duplicates data | Reject as completion requirement |
| Create a lazy overview image for each time | Small to moderate additional data | Faster zoomed-out first paint; exact viewport is still read from source | Optional later optimisation |

### Why a tree is unnecessary for the source grid

The result grid is rectangular and uniform. A viewport is transformed once to
local coordinates, then to integer row/column limits. Chunk IDs follow directly
from integer division by source chunk height and width. A spatial tree is
appropriate for irregular objects or sparse mesh faces, but would add lookup,
build, invalidation, and persistence complexity without reducing the regular
grid's candidate chunk count. The existing Adaptive/quadtree path is explicitly
outside this contract and can retain its own topology rules.

### Required mitigations for broad views

The server MUST not request native-resolution values for all chunks merely
because the map is zoomed out. It must render the requested output image at its
pixel budget and may sample within each decoded chunk for that image. This is a
display reduction only: point inspection and selected-area vector reads still
use native values. The source chunk cache uses the current viewport, one-ring
neighbours, selected time, and dynamic memory budget to make likely pans cheap.

An optional per-time overview may be generated after completion at low priority
or on first broad-view request. It must be explicitly labelled as a display
overview, must never replace native reads for numeric inspection, and must be
discardable/rebuildable. It is not needed for the initial recovery of the
failed run.

### Compatibility and migration

1. Existing NPZ-based imported archives remain on the existing reader path.
2. New regular runs write descriptors; Adaptive archives remain out of scope.
3. The result route selects the reader by descriptor schema versus legacy NPZ,
   without changing public URLs or Japanese UI labels.
4. Export must include all artefacts required by its selected reader. A
   descriptor without its NetCDF is invalid.
5. A feature flag or schema-version gate MUST permit rollback to the legacy
   path for small regular runs during migration, without treating the two
   formats as interchangeable files.

### Acceptance evidence for the adapted solution

The implementation is acceptable only when a retained 21-time,
`8000 x 8000` result can be finalized without allocating a dense 21-frame
array; its selected one-minute viewport can render; point inspection returns
all 21 native values; vectors use only viewport data; and a low-memory test
proves correct streaming behaviour rather than a process failure. These are
separate from the existing small-NPZ regression tests, which must continue to
pass.

## User experience requirements

### Current viewport and time

1. RESULT MUST render the selected time and visible map extent first.
2. Moving the time slider MUST use an already available one-minute frame
   immediately. A missing frame MUST be requested at its native output time;
   the UI MUST NOT substitute maximum depth or a neighbouring time.
3. The selected analysis boundary remains visible above every result layer.
4. Existing depth, vector, grid-resolution, opacity, and point-inspection
   interactions remain available.

### Map movement prefetch

Each meaningful map movement starts a new viewport generation. Work from an
older generation MUST NOT delay or overwrite the latest view.

| Trigger | Required work, in order |
| --- | --- |
| During movement | selected time in the visible extent only |
| 1 second after movement stops | selected time in surrounding tiles; favour the pan direction |
| 2 seconds after movement stops | selected time minus 1 minute, minus 2 minutes, and so on, nearest first, for the visible extent and already selected surrounding tiles |
| New pan or time selection | cancel stale prefetch and return to the first priority |

The system MAY subsequently prefetch future times only after all past times for
the idle viewport are available. Past-time prefetch is the required priority.

### Status

RESULT MUST retain a usable current layer while background loading occurs. It
MUST expose compact Japanese status text when relevant:

- `周辺を先読み中`
- `過去時刻を準備中: <loaded> / <total> 分`
- `この時刻を読み込み中`

Errors in background prefetch MUST not mark the completed simulation failed.

## Data and cache contract

1. `sfincs_map.nc` remains the immutable source of truth.
2. The read unit MUST align with the source NetCDF spatial chunk where
   possible. The current Full-output contract uses one time frame and
   2000-by-2000-cell chunks.
3. The display unit MAY be a smaller 500 m or 1000 m tile, composed from a
   cached source chunk. Re-reading the same compressed NetCDF chunk for each
   display tile is prohibited.
4. Cache identity includes run ID, result file identity, output time index,
   source-chunk row/column, and result-cache schema revision.
5. Each cached frame preserves native one-minute values, depth no-data policy,
   and the requested uniform block size.
6. Vectors are sampled only for presentation. Their time and direction remain
   those of the selected native frame.

## Dynamic memory budget

1. Cache capacity MUST be determined from currently available system memory,
   not a fixed number of frames.
2. The implementation MUST reserve a safety headroom before admitting data.
   It MUST never consume memory solely to reach a cache target.
3. When available memory falls, the cache MUST evict in this order:
   - stale viewport generations;
   - tiles outside the visible extent and its surrounding ring;
   - times furthest from the selected time;
   - least recently used remaining tiles.
4. The current visible extent at the selected time is protected from ordinary
   eviction. If it cannot fit safely, render the requested layer chunk by
   chunk without retaining it.
5. Disk-backed cache MAY retain recently decoded chunks, but disk cache is an
   optimization and must be safely invalidated by the same identity key.

## Completion criteria

- A 21-minute Full 1 m result with an 8000-by-8000 grid becomes viewable
  without constructing a 21-frame dense in-memory result array.
- A user can inspect every native one-minute time step for a selected
  viewport.
- A pan after idle prefetch loads the new selected time before old prefetch
  work continues.
- Cache pressure does not terminate a completed run or corrupt its NetCDF.
