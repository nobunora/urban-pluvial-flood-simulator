# Urban Pluvial Flood Simulator v0.1 — Setup Map and Run Progress UX Slice

> Status: Active implementation contract for PR #12
>
> Scope: minimal, review-ready UX improvement on the existing Full 1 m local review flow.
>
> User-visible behavior for this slice is defined first in `docs/specs/v0.1-setup-map-run-progress-ui-spec.md`.
>
> This document defines the implementation responsibilities and refactoring seams for two concrete usability gaps observed during hands-on review:
>
> 1. location/range selection is too difficult when only latitude/longitude fields are visible;
> 2. long-running preprocessing and SFINCS execution do not communicate enough visual activity or intermediate data flow.
>
> Product and system behavior remain governed by:
>
> 1. `docs/PRODUCT_SPEC_DRAFT.md`
> 2. `docs/specs/v0.1-implementation-spec.md`
> 3. `docs/specs/v0.1-ui-spec.md`
> 4. `docs/specs/v0.1-ui-implementation-spec.md`

>
> If this slice conflicts with a higher-priority contract, the higher-priority contract wins.

## 1. Goals

This slice SHALL make the current Full 1 m review flow understandable without requiring the user to reason directly from coordinates or wonder whether the engine has stopped.

Required outcomes:

1. SETUP shows a MapLibre/GSI map adjacent to the condition controls.
2. Clicking the setup map changes the selected analysis center.
3. The selected center remains reflected in the existing latitude/longitude fields.
4. The selected preset range is rendered as a square analysis-area overlay on the map.
5. Changing the range updates the square immediately.
6. During a run, the UI shows the ordered processing stages, current stage, completed stages, and the main data artifact obtained/generated by each completed stage.
7. During SFINCS execution the UI remains visibly active and shows elapsed time.
8. Official SFINCS `% complete` stdout telemetry may be shown when parsed; before it is available the indicator remains indeterminate. No fake numerical solver percentage is introduced.
9. Existing Full 1 m backend/API/hydraulic semantics remain unchanged.

---

## 2. Non-goals

This slice MUST NOT:

- implement Adaptive;
- add a second map engine;
- add a geocoding provider or address-search backend;
- add a general rectangle-drawing framework;
- change the analysis-area API shape;
- change rainfall semantics;
- change providers;
- change SFINCS model inputs;
- infer/guess percent-complete from undocumented text; only the documented/official SFINCS `% complete` output may drive solver progress;
- add dependencies;
- refactor the whole review UI into the final reducer/context architecture in the same change;
- change RESULT-map rendering semantics.

A later slice MAY add address/geocoder search and free rectangle drawing using the seams defined here.

## 3. Architectural principle

The implementation SHALL be minimal but SHALL separate responsibilities so the review UI can later migrate toward the canonical component architecture without rewriting behavior.

### 3.1 Existing `SmokeApp`

`SmokeApp` remains the workflow orchestrator for this review slice.

It owns:

- editable setup values;
- resource estimate request;
- run creation/cancellation;
- polling current run status;
- transition to existing RESULT view.

It MUST NOT directly own MapLibre instance lifecycle after this slice.

It MUST NOT contain the detailed stage visualization markup after this slice.

### 3.2 New `SetupMap`

`web/src/dev/SetupMap.tsx` owns setup-map rendering and map interaction only.

Inputs:

- numeric center latitude;
- numeric center longitude;
- current analysis bounds or null;
- disabled/read-only state while a run is active;
- callback for a user map click.

Responsibilities:

- initialize MapLibre once;
- use GSI standard raster tiles;
- show required GSI attribution;
- show one center marker;
- show one analysis-area GeoJSON source;
- show translucent fill + high-contrast outline;
- update marker and area geometry when props change;
- on map click, call the parent callback with longitude and latitude;
- fit the selected analysis area with padding when appropriate;
- destroy MapLibre resources on unmount.

It MUST NOT:

- construct RunConfig;
- call backend APIs;
- store canonical latitude/longitude separately from parent state;
- decide allowed range presets;
- calculate hydraulic grid semantics.

### 3.3 New `RunProgress`

`web/src/dev/RunProgress.tsx` owns run-stage presentation only.

Inputs:

- current `RunStatusResponse | null`;
- timestamp/monotonic marker for when the current stage was first observed;
- timestamp of the latest successful backend status poll.

Responsibilities:

- ordered stage visualization;
- completed/current/pending state;
- artifact/data badge for relevant stages;
- overall stage-count progress presentation;
- SFINCS indeterminate activity presentation;
- elapsed time during the currently observed stage;
- last successful status-check freshness.

It MUST NOT:

- create/cancel runs;
- poll the backend;
- mutate run lifecycle;
- infer hydraulic correctness;
- invent solver percentage.

### 3.4 Styling

Existing `web/src/dev/smoke.css` remains the review-layout stylesheet.

Map-specific and progress-specific class names SHALL be prefixed:

- `setup-map-*`
- `run-progress-*`

This keeps future extraction mechanical.

## 4. Setup map behavior

### 4.1 Base map

Map engine: MapLibre GL JS 6.x.

Raster source:

`https://cyberjapandata.gsi.go.jp/xyz/std/{z}/{x}/{y}.png`

Attribution:

`国土地理院`

Default initial center is the current latitude/longitude state.

The map SHALL be visibly larger than the raw coordinate fields so location can be selected spatially.

### 4.2 Selecting a location

When no run is active:

- clicking the map selects that longitude/latitude;
- the center marker moves immediately;
- latitude and longitude text inputs update to six decimal places;
- analysis area is recomputed from the existing range preset;
- the area square moves with the selected center.

When a run is active:

- setup-map location mutation is disabled;
- the map MAY remain visible but SHALL not alter the active RunConfig.

Direct latitude/longitude inputs remain available as a fallback and expert correction path.

### 4.3 Range rectangle

The existing preset values remain:

- ±250 m
- ±500 m
- ±1000 m
- ±2000 m

The existing `squareArea` calculation remains the RunConfig source for this slice.

The setup map SHALL render the resulting bounds as a rectangle:

- translucent fill;
- visible outline;
- visually distinguishable from GSI roads/buildings;
- no result-depth color semantics.

Changing the preset SHALL update the map rectangle immediately.

### 4.4 Fit behavior

On first usable map render, center the map on the selected center.

When the analysis bounds change, the map SHOULD fit the bounds with approximately 32–48 px padding, subject to a reasonable maximum zoom.

The fit action MUST NOT trigger another location selection.

### 4.5 Accessibility/instructions

Visible helper copy:

`地図をクリックして解析中心を選択できます。四角い枠が解析範囲です。`

Coordinate fields remain labelled.

The map container uses a descriptive ARIA label such as:

`解析場所と範囲を選択する地図`

## 5. Run progress information model

The existing backend stage codes remain authoritative.

Ordered stages for presentation:

1. `CREATED` — 受付
2. `VALIDATING` — 入力確認
3. `ACQUIRING_TERRAIN` — 標高取得
4. `ACQUIRING_VECTORS` — 建物・道路取得
5. `ACQUIRING_RAINFALL` — 降雨準備
6. `PREPROCESSING_TERRAIN` — 地形前処理
7. `ALLOCATING_ROOF_RAIN` — 屋根雨水配分
8. `BUILDING_GRID` — 1 m格子構築
9. `BUILDING_MODEL` — SFINCSモデル構築
10. `ENSURING_ENGINE` — エンジン確認
11. `RUNNING_ENGINE` — SFINCS計算
12. `READING_RESULTS` — 結果読込
13. `COMPLETE` — 完了

`CANCELLING`, `CANCELLED`, and `FAILED` are terminal/exception states and are displayed separately rather than inserted into the normal completion sequence.

## 6. Data/artifact visualization

The progress UI SHALL make the produced/acquired data flow understandable.

Relevant stage artifact badges:

| Stage | Visual artifact label | Meaning |
|---|---|---|
| ACQUIRING_TERRAIN | 標高 | elevation data acquired |
| ACQUIRING_VECTORS | 建物・道路 | vector data acquired |
| ACQUIRING_RAINFALL | 雨 | rainfall time series/scenario prepared |
| BUILDING_GRID | 1 m格子 | computational grid generated |
| BUILDING_MODEL | モデル | SFINCS model files prepared |
| ENSURING_ENGINE | SFINCS | compatible engine resolved |
| RUNNING_ENGINE | 計算 | hydraulic calculation executing/executed |
| READING_RESULTS | 結果 | output read/normalized |
| COMPLETE | 地図 | result view available |

A badge becomes visually complete only once the run has advanced beyond the associated normal stage, or the run is `COMPLETE`.

These badges indicate workflow completion, not independent scientific validation.

Use compact icons/symbols together with text; the text label is mandatory so meaning does not depend on emoji rendering.

## 7. Progress semantics

### 7.1 Pipeline progress

A segmented/linear pipeline indicator MAY represent position in the known ordered application stages.

If a numeric fraction is shown, it SHALL mean:

`completed/entered application stages / total application stages`

It MUST NOT be labelled as SFINCS computation percentage.

Preferred UI copy:

`工程 10 / 13`

### 7.2 SFINCS execution

The backend parses the official SFINCS stdout `% complete` signal.

While `RUNNING_ENGINE` is active:

- before a real progress sample exists, show an indeterminate activity indicator;
- show `SFINCS計算中`;
- show elapsed time since the browser first observed `RUNNING_ENGINE`;
- show the freshness of the latest successful `GET /runs/{id}` poll;
- once a real sample exists, show the actual percentage;
- calculate remaining-time estimate from elapsed wall time and actual progress fraction.

Example:

`SFINCS計算中 — 40% — 経過 00:12`

`状態確認: 1秒以内 / 残り目安 約00:18（実進捗から推定）`

The engine's own rough remaining-seconds text is diagnostic only and is not used as the sole displayed ETA.

### 7.3 Other stages

For non-engine active stages:

- current stage is highlighted;
- an indeterminate/current-stage animation MAY be used;
- elapsed time since stage observation MAY be shown.

### 7.4 Poll liveness

The current review UI already polls `GET /runs/{id}` approximately once per second.

A successful response updates `last successful status check`.

The visual liveness indicator means only that the local application is responding. It MUST NOT claim the solver itself is making numerical progress.

## 8. State transition details

`SmokeApp` SHALL track:

- current status;
- current observed stage code;
- browser timestamp when that stage code first appeared;
- browser timestamp of latest successful status poll.

When `stage_code` changes:

- reset the current-stage observed timestamp.

When a successful status poll returns the same stage:

- update last successful poll timestamp only;
- do not reset stage elapsed time.

When terminal state is reached:

- stop the polling interval using the existing terminal rule.

When `新しい解析` is selected:

- clear run/progress transient state while retaining setup inputs according to the existing RESULT contract.

---

## 9. Failure/cancellation behavior

If state is `FAILED`:

- retain the existing failure code/message;
- progress visualization shows a failure state;
- completed artifact badges remain visible for already-passed stages when inferable from prior observed stage;
- do not show COMPLETE.

If state is `CANCELLING`:

- show cancellation in progress.

If state is `CANCELLED`:

- show cancelled terminal state.

This slice does not add persistence of full stage history across page reloads.

---

## 10. Backend/API boundary

This slice SHALL NOT change the backend API contract.

Reasons:

- current stage code/label are already available via `RunStatusResponse`;
- current review polling is sufficient for stage visualization;
- SFINCS does not currently expose a trustworthy documented percent-complete signal;
- avoiding an API change keeps this UX slice isolated.

Future enhancement seam:

- `/runs/{id}/events` SSE already exists;
- a later refactor may move `RunProgress` data sourcing from polling to SSE without changing the presentation component contract materially;
- a later solver adapter may expose real progress only if based on documented/reliable SFINCS telemetry.

## 14. Refactoring seam

This slice intentionally avoids the full canonical `useReducer + Context` migration.

The new components SHALL be written so a later refactor can:

- move setup values from `SmokeApp` into canonical setup state without changing `SetupMap` behavior;
- move run lifecycle from polling state into canonical reducer/SSE without changing `RunProgress` presentation semantics;
- move `SetupMap` from `dev/` to `map/MapView` or `components/LocationStep` by changing imports rather than reimplementing map behavior.

No shared backend/domain contract should be coupled to the review-only component paths.
