# v0.1 visibility, execution feedback, parallelism, and building-completeness specification

> Status: Active implementation contract for PR #12
>
> Scope: Full 1 m review flow. Adaptive remains unavailable.

## 1. RESULT visibility contract

All analysis products are primary overlays and MUST remain fully visible:

- maximum flood depth;
- time-dependent flood depth;
- computational grid;
- flow vectors.

The opacity control SHALL affect only the GSI basemap.

UI label:

`背景地図の透明度`

Range: 0–100%, default 45%.

- 0% = no transparency (basemap fully visible);
- 100% = basemap fully transparent/hidden;
- result raster remains opacity 1.0;
- flow vectors remain opacity 1.0;
- red analysis boundary remains visible above all overlays.

The RESULT map SHALL use two physically separate MapLibre canvases:

1. a non-interactive GSI basemap canvas whose DOM/CSS opacity is controlled directly;
2. an interactive transparent analysis-overlay canvas containing result raster, optional flow vectors and the analysis boundary.

Changing a result layer/time SHALL rebuild the analysis-overlay map with the exact selected image URL instead of relying on late `ImageSource.updateImage` / style-load timing. Basemap transparency therefore cannot fade result products.

## 2. Address/place selection map movement

Selecting a geocoder candidate SHALL:

1. update canonical longitude/latitude;
2. update the center marker;
3. update the analysis square;
4. immediately stop any previous camera animation;
5. resize and fit the visible SETUP viewport to the selected analysis square.

Viewport movement MUST NOT wait on MapLibre style/source load state. Source-data refresh may wait for source readiness; camera movement may not.

Direct coordinate edits and map-click selection continue to use the same canonical location state.

## 3. Consolidated run-progress presentation

The detailed 13-state backend state machine remains unchanged for provenance and API compatibility.

The UI SHALL consolidate these into five meaningful user-facing boxes:

1. **準備** — CREATED, VALIDATING
2. **データ取得** — ACQUIRING_TERRAIN, ACQUIRING_VECTORS, ACQUIRING_RAINFALL
3. **解析格子** — PREPROCESSING_TERRAIN, ALLOCATING_ROOF_RAIN, BUILDING_GRID, BUILDING_MODEL, ENSURING_ENGINE
4. **SFINCS計算** — RUNNING_ENGINE
5. **結果** — READING_RESULTS, COMPLETE

Existing artifact icons SHALL be integrated into the corresponding box. The separate lower artifact row SHALL be removed.

The current exact backend stage label remains visible in the summary so detailed state is not lost.

## 4. Live activity / console view

Long-running operations SHALL expose recent activity lines through `RunStatusResponse.activity_lines`.

The backend keeps a bounded recent buffer; it is not a replacement for persisted logs.

Activity lines include:

- stage start messages;
- cache hit/miss messages;
- PLATEAU file count, processed/remaining files and current building/road counts;
- OSM processed/remaining elements and current building/road counts;
- Full 1 m parallel preprocessing task count and remaining task count;
- blocked building-cell count and road-cell count;
- roof/building-component allocation processed/remaining counts;
- model build start/completion;
- actual SFINCS stdout lines while RUNNING_ENGINE;
- result-read start/completion.

`RunStatusResponse.progress_fraction` and `progress_detail` SHALL expose this live provider/grid work so the UI can show a visible per-stage progress bar in addition to the console.

The UI shows the latest lines in a console-style `<pre>` panel for long-running grouped stages.

SFINCS stdout continues to be persisted verbatim in `sfincs.stdout.log`.

## 5. CPU / parallel execution

### 5.1 SFINCS

Upstream SFINCS CPU builds use OpenMP. The launcher SHALL explicitly set:

- `OMP_NUM_THREADS = os.cpu_count()` (minimum 1);
- `OMP_DYNAMIC = FALSE`.

The existing executable is not replaced or rebuilt.

The app SHALL NOT promise literal 100% utilization because I/O, synchronization and serial regions can prevent it, but it SHALL request all logical CPUs from the OpenMP runtime.

### 5.2 Full 1 m preprocessing

Independent CPU-heavy preparation steps SHALL run concurrently in a bounded thread pool:

- terrain center conversion;
- building rasterization;
- road rasterization.

The worker count is bounded by available CPUs and the number of independent tasks.

No nested unbounded executor is allowed.

## 6. Building completeness

The hydraulic rule remains:

- any cell touched by a building footprint is a building/blocked cell;
- no minimum building area threshold;
- `all_touched=True` at 1 m rasterization.

To reduce missing small buildings:

- OSM query includes both `building` / `building:part` ways and relations;
- PLATEAU `BuildingPart` is treated as a building obstacle;
- in auto mode, OSM is used as a **building supplement even when PLATEAU succeeds**;
- PLATEAU and OSM acquisition run concurrently while PLATEAU remains the primary provenance source;
- building footprints are union-by-rasterization semantics: duplicate/overlapping polygons are harmless;
- PLATEAU transportation geometry remains primary; OSM road lines may supplement it;
- provenance records a combined provider when both succeed.

If one provider fails, the successful provider remains usable with an explicit warning.

Prepared Full 1 m cache revision is `full1m-preprocess-v3-all-building-obstacles`, so v1/v2 grids built under older building-completeness contracts are not reused.

### 6.1 Building geometry detail / map scale

Building obstacles MUST NOT be inferred from the rendered GSI basemap or any zoom-dependent raster/vector-tile representation.

- The rectangular analysis area is only the spatial query/clip boundary.
- Each building retains native PLATEAU CityGML or OSM Overpass polygon geometry.
- No browser map zoom level is used to decide whether a building exists.
- No geometry simplification is applied before Full 1 m rasterization.
- Provider provenance records:
  - `building_geometry_detail = native-full-detail`;
  - `map_zoom_dependent = false`;
  - `geometry_simplification = none`.
- Full 1 m rasterization then applies `all_touched=True` to those native polygons.

This is the maximum-detail contract. The user's "largest map scale" requirement is implemented by bypassing rendered-map scale entirely and using the source vector geometry itself.

### 6.2 RESULT sidebar / fullscreen focus

Normal RESULT sidebar order SHALL be:

1. point inspection;
2. current legend;
3. `結果概要` (closed by default);
4. `解析条件と出典` (closed by default);
5. model limitations.

The legend occupies the sidebar position previously used by the always-open result summary.

The `全画面` control SHALL request the browser Fullscreen API for a focused RESULT region. In fullscreen, the visible content is limited to:

- map;
- point inspection;
- legend;
- fullscreen-exit control.

Result summary, provenance/details, model limitations, header, layer controls and other surrounding UI are excluded or hidden from the fullscreen focus surface.

## 9. Time-depth interaction performance and vector flow rendering

### 9.1 Time-depth target

Moving the time-depth slider MUST NOT recreate either MapLibre instance.

The performance path is:

1. normalized arrays are LRU-cached by result artifact path + mtime;
2. rendered time-depth PNG bytes are LRU-cached by path + mtime + actual time index + render size;
3. layer responses use immutable browser-cache headers because run IDs/artifacts are immutable;
4. RESULT starts bounded prefetch of every available time-depth frame while the user is initially viewing maximum depth;
5. prefetched frames are retained as in-memory Blob URLs when the browser supports them;
6. slider movement changes only the existing MapLibre ImageSource URL.

For already prefetched/cached frames, the product target is approximately **50 ms class interaction latency** from slider input to image-source update on the local review environment. This is a performance target, not a hard cross-machine SLA; first uncached rendering, disk I/O, image decode, GPU scheduling and browser load may exceed it.

No new SFINCS computation is triggered by moving the RESULT time slider.

### 9.2 Flow vectors are native vector geometry

Flow arrows SHALL NOT use PNG/raster rendering.

The only current flow-display API is:

```text
GET /api/v1/runs/{run_id}/layers/flow-vectors.geojson?time_index=<actual-index>&max_vectors=<n>
```

The former `flow-vectors.png` endpoint and raster renderer are removed.

Each sampled arrow is a GeoJSON `MultiLineString` containing:

- shaft;
- two arrow-head segments;
- `speed_mps = sqrt(u² + v²)`;
- mean `u_mps`;
- mean `v_mps`;
- actual `time_index`.

MapLibre draws these features with a native `line` layer. Arrow direction represents flow direction. Arrow color represents **flow speed (m/s)**.

The flow-speed legend is separate from depth/grid legends:

- 0.001–0.10 m/s — #2DC4B2
- 0.10–0.30 m/s — #3BB2D0
- 0.30–0.50 m/s — #3F51B5
- 0.50–1.00 m/s — #8E44AD
- 1.00–2.00 m/s — #E74C3C
- 2.00 m/s以上 — #7F0000

Flow quantity/discharge is intentionally not used for color in this slice because discharge would require an additional explicit cross-sectional definition.

### 9.3 Flow visibility robustness

Real-browser acceptance requires the vector overlay to remain visible under mixed local flow directions and against both the basemap and depth raster.

- Sampling SHALL select the maximum-speed valid wet cell inside each display block instead of averaging u/v across the block. This prevents opposite local directions from cancelling to zero.
- The minimum displayed speed is 0.001 m/s.
- Enabling flow vectors on an output time with zero arrows SHALL automatically search the nearest available output times until a non-empty flow-vector set is found. Manual time changes after that remain user-controlled.
- The browser SHALL fetch GeoJSON explicitly and pass the parsed FeatureCollection directly to MapLibre `GeoJSONSource.setData`; MapLibre is not responsible for fetching the API URL internally.
- Flow vectors use a white halo line beneath the speed-colored line for visibility on both light and dark result backgrounds.
- The UI reports the current rendered arrow count and distinguishes loading, no-vector-at-this-time, and request failure states.

### 9.4 Analysis boundary visibility

The analysis boundary SHALL use a closed GeoJSON `LineString`, not a fill edge.

It is drawn above all result/vector layers with:

1. an 8 px white casing;
2. a 4 px opaque red `#DC2626` line.

Both boundary layers are explicitly kept visible whenever result or vector data updates.
