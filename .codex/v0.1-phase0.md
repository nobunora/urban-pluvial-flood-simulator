# v0.1 Phase 0 — SFINCS Compatibility Spike

Use this contract for the **next implementation PR only**.

Canonical specification:

- `docs/specs/v0.1-implementation-spec.md`

Supporting contracts:

- `docs/PRODUCT_SPEC_DRAFT.md`
- `docs/specs/v0.1-ui-spec.md` only for context; do not implement UI in Phase 0.

## Objective

Prove that the exact v0.1 hydraulic integration baseline can be constructed and executed before any application/UI architecture is built.

Phase 0 answers one question only:

> Can pinned HydroMT-SFINCS and SFINCS produce and execute the required regular, quadtree, and subgrid model forms, with results readable deterministically by this repository?

## Approved baseline

Use exactly:

- Python 3.12.x reference environment;
- SFINCS v2.4.0 Galibier;
- `hydromt_sfincs==2.0.0rc3` unless the canonical specification has been revised before this task starts;
- Xarray/NetCDF for direct result-read proof when needed.

Do not track `latest`.

## Repository procedure

1. Read `AGENTS.md`.
2. Read this file.
3. Read only `docs/specs/v0.1-implementation-spec.md` sections 0, 2, 20, 21, 22 and the minimum dependency/build files needed for the spike.
4. Query CodebaseMemory first when available.
5. Use `git`, `rg`, targeted file reads, Python/package metadata, and the dependency-native tooling required by the spike.
6. If `scripts/repo_query.py` or `scripts/analyze.py` is absent, record `optional-wrapper-unavailable` and continue with the underlying deterministic tools. Their absence is **not** a Phase 0 blocker.
7. Do not scan the whole repository or implement unrelated tooling.

## Phase 0 scope — required work

Create the smallest deterministic compatibility harness/fixtures needed to prove all of the following:

1. **Regular model build**
   - HydroMT-SFINCS creates a tiny regular-grid SFINCS model.
   - Required files are written without manual post-editing.

2. **Quadtree model build**
   - HydroMT-SFINCS creates a tiny quadtree model using the pinned dependency versions.
   - Grid hierarchy is readable/inspectable after write.

3. **Subgrid model build**
   - A tiny model with high-resolution elevation/roughness input produces valid SFINCS subgrid tables.
   - The test records the source raster resolution and hydraulic grid resolution separately.

4. **SFINCS execution**
   - SFINCS v2.4.0 executes at least one deterministic tiny fixture to normal completion.
   - Zero-rain/flat-domain behavior must not create NaN/Inf or non-zero water from nothing.

5. **Result-read proof**
   - Repository code or a spike script reads required result variables deterministically.
   - Direct Xarray/NetCDF reading is allowed and preferred if the HydroMT result reader is unstable.
   - Variable names, dimensions, coordinate orientation, units, and no-data handling used by the proof are recorded.

## Required evidence

The PR must add a report at:

```text
docs/implementation/v0.1-phase0-report.md
```

The report must contain:

- exact Python version;
- exact package versions;
- SFINCS version/build identity and acquisition route;
- operating system used for validation;
- exact environment creation/install commands;
- exact commands for each of the five checks;
- pass/fail result for every check;
- output file names needed for later implementation;
- discovered SFINCS/HydroMT variable/file contracts;
- warnings or deprecations that could affect Phase 1–4;
- unresolved license/distribution constraints, if any;
- final disposition: `validated` or `spec-change-required`.

Do not commit large generated model outputs. Keep only tiny fixtures/configuration or textual summaries needed for deterministic tests.

## Explicitly out of scope

Do **not** implement or refactor any of the following in Phase 0:

- FastAPI application;
- React/Vite/MapLibre UI;
- geocoding;
- JMA rainfall catalog;
- production GSI provider refactor;
- production PLATEAU provider refactor;
- OSM provider refactor;
- roof-rainfall algorithm changes;
- Full 1 m end-to-end application flow;
- Adaptive classification/coarsening policy;
- result renderer/UI PNG layers;
- SFINCS engine bootstrap/distribution UX;
- packaging;
- sewer, infiltration, river, tide, or spatial-rain features;
- another hydraulic engine;
- new repository-index/static-analysis wrappers merely because docs describe them.

Existing native `src/solver.cpp` is reference code. Do not delete, replace, or rewrite it during this spike.

## SFINCS binary/license rule

Do not commit or redistribute a Deltares binary whose distribution terms do not permit redistribution.

For Phase 0, a locally obtained permitted SFINCS executable may be used for validation. Record exactly how it was obtained. Product redistribution/managed-build strategy is a later release concern unless the spike proves that the planned strategy is impossible.

The repository's own final license selection is **not** a Phase 0 compatibility blocker, but it must be resolved before broad binary/source distribution.

## Stop conditions

Return `spec-change-required` and stop without starting Phase 1 if any of these is true:

- `hydromt_sfincs==2.0.0rc3` cannot construct one of regular/quadtree/subgrid models required by the specification;
- SFINCS v2.4.0 cannot execute the generated minimal model without an unapproved manual format rewrite;
- required result quantities cannot be read deterministically;
- the actual file/schema contract materially contradicts the detailed implementation specification;
- continuing would require changing engine, pinned major architecture, numerical meaning, or external-license assumptions;
- a required dependency is unavailable from a legitimate source.

Do not silently downgrade HydroMT-SFINCS, switch engines, or create a parallel custom SFINCS writer.

## Clear conditions

Phase 0 is complete only when all five compatibility checks pass and the report is committed.

Before marking the PR ready, run all focused tests introduced by the spike plus existing tests affected by dependency/environment changes. Do not claim checks that were not run.
